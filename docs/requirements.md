# tecupid 要件定義書

- 版: 0.1（ドラフト）
- 作成日: 2026-11-22
- ステータス: 検討中（「10. 未決事項」を参照）

---

## 1. 概要

tecupid は、エンジニアが次に学ぶ技術を選ぶのを助ける Web アプリケーションである。

**キャッチコピー: 「エンジニアのための技術マッチングアプリ」**（7.1 のとおり、マッチングの相手が「技術」であることが分かる形で使う）

> This is a web application that supports you in selecting a new technology to learn.

マッチングアプリのように「技術の特徴」が書かれたカードが 1 枚ずつ表示される。ユーザーは気に入れば ❤（Like）、気に入らなければ ✕（Nope）を選ぶ。その結果から、ユーザーの好みに合う技術を推薦する。

ポイントは、技術名ではなく**特徴**を見せることである。「Rust」という名前に対する先入観ではなく、「メモリ安全性をコンパイラが保証してくれる」といった特徴への反応で判断してもらう。

## 2. 目的と成功の基準

| 目的 | 基準（MVP） |
|---|---|
| 学ぶ技術を短時間で選べる | 1 セッション 3 分以内（カード 15〜20 枚）で結果が出る |
| 推薦に納得できる | 結果画面で、推薦理由（どの ❤ が効いたか）が分かる |
| すぐ学び始められる | 推薦された技術ごとに公式ドキュメントや入門資料へのリンクがある |
| 安心して使える | 個人情報を取得しない。規約・免責・プライバシーの方針を明記する |

## 3. 対象ユーザー

- **主対象**: 学生エンジニアと若手エンジニア。1 つ目か 2 つ目の言語・技術を学んでいて、次に何を学ぶか迷っている人。
- **副対象**: 新しい分野に手を広げたい中堅エンジニア。

## 4. スコープ

### 4.1 MVP に含めるもの

- 特徴カードのスワイプ（❤ / ✕）
- タグのスコアリングによる推薦
- 結果画面（上位 3 件、推薦理由、学習リソースへのリンク）
- やり直し、結果のシェア（URL またはテキスト）
- 利用規約、免責事項、プライバシーポリシーの各ページ

### 4.2 MVP に含めないもの

- ユーザー登録とログイン
- **人と人をマッチングする機能**（メッセージやプロフィール公開など）。入れると法的な扱いが大きく変わるため、恒久的な対象外とする（7.1 参照）
- 広告、アフィリエイト、課金
- アクセス解析ツール（入れる場合は 7.3 の対応を先に行う）
- LLM による推薦

## 5. 機能要件

### F-1 トップ画面

- サービスの説明と「はじめる」ボタンを表示する。
- 経験レベルを 0（まったくの初心者）〜 10（自信あり）のスライダーで選んでもらう。初期値は 5。レベルによって、出すカード（F-2）と推薦（6.2）が変わる。
- 「推薦は学習の参考情報である」と短く表示し、免責事項へのリンクを置く。

### F-2 カードスワイプ画面

- 特徴カードを 1 枚ずつ表示する。カードには特徴の文と、補足の短い例を載せる。**技術名は載せない**。
- 操作方法は次のとおり。
  - 「すき」ボタンと「興味なし」ボタン（主な操作）。既存のマッチングアプリの言い回しと重ならないよう、「LIKE」「NOPE」などは使わない（7.6）
  - 左右へのスワイプ（補助の操作。タッチとマウスの両方に対応する）
    - 80px 以上ドラッグするか、30px 以上を素早くはじいたら（0.35px/ms 以上）回答とみなす。スマホでは短くはじくスワイプが多いため。
    - カードの上では `touch-action: none` にして、ブラウザが縦のスクロールと判断してスワイプを打ち切らないようにする（答える画面は 100svh に収まるので、スクロールは要らない）。
    - 指の操作はタッチイベントで受け取り、マウスとペンはポインターイベントで受け取る。iPhone の Safari では、ポインターイベントだけだとスワイプができなかったため（ベータ版のフィードバック）。touchmove で `preventDefault` して、ブラウザのスクロールや「戻る」の操作にしない。
  - キーボードの ← と →
- 1 セッションで出すカードは 15〜20 枚とする。カードはカテゴリが偏らないように選ぶ。
  - 最初の山札は 20 枚（分野 9、言語の性質 6、フレームワークの性質 3、開発環境とエコシステム 2）。分野の 9 枚には、どの部門についても関心を聞くカードを必ず 1 枚以上入れる。残りの枠で、低レイヤやクロスプラットフォームなど、部門になっていない分野のカードも出す。
  - 最初の山札を答え終えたら、関心があると判定した部門（6.6）の専用カードを最大 4 枚追加で出す。カードに条件（`requires`）があるときは、そのタグの好みが 0 より大きい人にだけ出す（例: iPhone 向けか Android 向けかを聞くカードは、モバイルに関心がある人にだけ出す）。追加のカードには「〇〇に関心がありそうなので、追加の質問です」と表示する。
- 進捗（何枚目か）を表示する。
- スワイプできることに気づいてもらう: 最初のカードを一度だけ左右に揺らす。カードの中に「← 興味なし ／ すき →」と方向を書く（ベータ版のフィードバックで、スワイプに気づかなかったという声があったため）。
- 選んだ感を出す: 答えると、カードがその方向へ飛んでいき、中央に大きな「すき！」「興味なし」のスタンプを出す。スワイプ、ボタン、キーのどれで答えても同じ演出にする。対応している端末では、短く振動させる。`prefers-reduced-motion` のときは演出をしない。
- カードに答える画面は、スクロールしなくても全体が見えるよう、画面の高さ（100svh）に収める。カードの高さを伸び縮みさせ、この画面ではフッターを隠す。360 × 640 の画面でも収まることを確かめている。
- 直前の 1 枚を取り消せる。
- 途中でも「結果を見る」を押せる。ただし最初の山札の 4 分の 3（20 枚なら 15 枚）は答えてもらう。
  - 根拠: `scripts/simulate-min-answers.ts` で、好みの異なる架空のユーザー 2,000 人に答えさせた。途中までの回答で出した 1 位が、最初の山札をすべて答えたときの 1 位と一致した割合は、8 枚で言語 43%・フレームワーク 15%、15 枚で 66%・52%、18 枚で 80%・80% だった（2026-11-24、Lisp 追加後）。架空のユーザーの好みはランダムなので、実際の人より悲観的な見積もりだが、8 枚では早すぎると判断した。
- 経験レベルが 3 以下の人には、専門用語の多いカード（`advanced`）を出さない。対象は feature-cards.md の 5 章。

### F-3 結果画面

- 結果は**部門別**に表示する（部門の一覧は 6.6）。
  - いちばん上に、おすすめの組み合わせを 1 件出す（例: 「TypeScript ＋ React」。6.2 の手順 6）。
  - 次に言語部門、続いて関心があると判定した部門を、関心度の高い順に出す。各部門は上位 3 件。
  - 上に展開する部門は、言語を含めて最大 3 部門にする。部門が増えても画面が長くなりすぎないようにするためである。
  - 関心がないと判定した部門と、4 番目以降の部門は、下の「そのほかの部門」に折りたたんで置く。
- 各技術について次を表示する。
  - 技術名、カテゴリ、1〜2 行の概要
  - マッチ度: すべての部門で最もスコアの高い技術を 100 とした値と、5 つのハートのメーター。コサイン類似度の絶対値は 0.4〜0.7 程度に収まりやすく、そのまま出すと 1 位でも低く見えるため、相対値にする
  - 推薦理由: スコアへの寄与が大きかった「すき」のカード（最大 3 枚）。画面を短くするため、各部門の 1 位にだけ出す
  - 学習リソースのリンク（公式ドキュメント、公式チュートリアルなど）
- 「4 位以下も見る」で、部門ごとの全体のランキングを開ける。
- 「もう一度やる」ボタンを置く。

### F-4 シェア

- 結果をテキストでコピーできる。例: 「tecupidで『Go ＋ Gin』にマッチングしました！」（技術「マッチング」アプリなので「マッチングしました」と言う。日本語と英字のあいだに半角スペースを入れない）
- 結果を URL で共有できる。URL には技術の ID だけを入れ、回答の中身は入れない。
- 実装:
  - シェアするのは、おすすめの組み合わせ（なければ言語の 1 位）。シェアされうる結果は「言語 ＋ フレームワーク」の 23 通りと、言語だけの 13 通りに限られる。
  - そのすべてについて、シェア用のページ（例: `/m/typescript/react/`）をビルド時に静的に作る。シェア用のページを開くと、スタート画面の上に「友だちのマッチング結果」を出す。
  - SNS で共有したときのサムネイル（OGP 画像、1200 × 630）も、結果ごとに `public/og/` に用意する。`npm run og` で作り、技術を追加したり名前を変えたりしたら作り直す。画像がない結果があると、テストが失敗する。
  - シェアの枠は、結果画面の「おすすめの組み合わせ」のすぐ下に、目立つように置く。投稿する文章と URL をテキストボックスで見せ、手でもコピーできるようにする（タップすると全体を選択する）。「X でポスト」と「コピー」のボタンを並べる。
  - SNS の共有ボタンは、ひとまず「X でポスト」だけにする（LINE などは付けない）。投稿する文章の最後には、ハッシュタグ `#tecupid` を付ける（技術名のハッシュタグは付けない）。ほかに「URL をコピー」を置く。各サービスのロゴ（商標）は使わず、文字だけにする。
  - OGP の画像の URL は絶対 URL にする必要があるため、ビルドするときに環境変数 `SITE_URL` で本番の URL を指定する。未指定のときは、OGP の画像と URL のメタタグを出力しない。

### F-5 静的ページ

- 利用規約、免責事項、プライバシーポリシー、このサービスについて（運営者の連絡先を含む）
- 実装済み: `/terms/`、`/disclaimer/`、`/privacy/`、`/about/`、404 ページ。全ページのフッターからリンクする。
- 文面は運営者が下書きしたもので、専門家の確認は受けていない。公開範囲を広げる前に確認する（10 章）。

## 6. データと推薦ロジック

### 6.1 データモデル

データはリポジトリ内の JSON か TypeScript ファイルで管理する。データベースは使わない。

```ts
type Tag = string; // 6.5 の一覧のいずれか。例: "static-typing", "gc", "web-frontend"

// 重みは −1.0〜1.0。
//   +1 = その性質がはっきり当てはまる
//   −1 = 反対の性質がはっきり当てはまる（例: gc が −1 なら、GC がなくメモリを自分で管理する）
//    0 = どちらでもない、または該当しない（省略してよい）
type TagWeights = Partial<Record<Tag, number>>;

type FeatureCard = {
  id: string;
  text: string;          // 例: "メモリの確保と解放を自分で制御できる"
  example?: string;      // 補足の短い例
  axis: "domain" | "language" | "framework" | "department" | "ecosystem"; // カードの偏りを防ぐ分類
  department?: string;   // axis が department（部門の専用カード）のとき、どの部門のカードか
  advanced?: boolean;    // 専門用語が多いカード。経験レベルが 3 以下の人には出さない
  requires?: string;     // 追加で出すのは、このタグの好みが 0 より大きいときだけ
  tags: TagWeights;      // 例: { gc: -1, "native-compile": 1 }
};

type Technology = {
  id: string;            // 例: "rust"
  name: string;
  department: string;    // 6.6 の部門。例: "language", "framework", "infra"
  category?: "frontend" | "backend" | "mobile"; // department が framework のとき
  languages?: string[];  // department が framework のとき、使う言語の id。例: React → ["javascript", "typescript"]
  summary: string;
  tagWeights: TagWeights;
  evidence: Partial<Record<Tag, string>>; // 重みが 0 でないタグごとの根拠（公式ドキュメントの URL など）
  resources: { title: string; url: string; official: boolean }[];
};
```

### 6.2 スコアリング

1. 回答から、ユーザーのタグ選好ベクトルを作る。
   - ❤ のカード: カードの `tags` の重みをそのまま足す
   - ✕ のカード: カードの `tags` の重みに −1 を掛けて足す（係数は調整できるようにする）
   - 経験レベルに応じた初心者向けの補正を足す。`{ simple-syntax: 1, gc: 1, fast-feedback: 1, maturity: 0.5 }` に、「(10 − レベル) ÷ 10 × 1.5」を掛けたもの。LV.0 で最も強く、LV.10 では足さない。
   - 補正に使うのは、学び始めやすさに関係し、客観的に判定できるタグだけにする（覚える文法が少ない、メモリ管理を自分でしなくてよい、すぐ結果を確かめられる、歴史が長い）。
   - 例: まったくの初心者（LV.0）がまだ何も答えていなければ Python が 1 位になる。初心者が「Web の画面を作りたい」とだけ答えた場合は、JavaScript が 1 位になる（TypeScript より上）。
2. 選好ベクトルと各技術の `tagWeights` に、軸ごとの重みを掛ける。初期値は分野の軸と部門の性質の軸を 2 倍、ほかは 1 倍とする。
   - 理由: 分野のタグは 1 つの技術に 1〜2 個しかなく、8 個ある言語の性質のタグに埋もれやすい。シミュレーションでは、1 倍のままだと「Web の画面を作りたい」人に Dart が 1 位になるなど、分野の好みが反映されにくかった。
   - 部門の性質（部門の中で技術を区別するタグ）も 2 倍にする。知識の分野のトピックは、関係する分野のタグ（2 倍）を多く持つため、1 倍のままだと「線形代数」のカードに「すき」と答えても、数学部門で微分積分が 1 位になるなど、トピックの内容が反映されにくかった。
3. 重みを掛けた 2 つのベクトルから、スコアを計算する。
   - 分野のタグと、それ以外のタグ（言語の性質など）に分け、それぞれで類似度を求める。2 つを、ユーザーの選好ベクトルのそれぞれの部分の大きさ（どちらにどれだけ答えたか）で重み付けして平均する。
   - それぞれの類似度はコサイン類似度とする。タグ数の多い技術ばかりが有利にならないようにするためである。
   - ただし分野の類似度では、技術の分野のベクトルの大きさを、最低でも重み 1 のタグ 1 つ分とみなす。0.5 の分野（公式のツールで対応している程度）しか持たない技術が、その分野の専門の技術と同じ点数にならないようにするためである。
   - 分野のカードへの「興味なし」は、順位付けには使わない（選好ベクトルの分野のマイナスの値を 0 にする）。「興味がない」は「嫌い」ではないためである。部門の関心度（6.6）には、マイナスの値もそのまま使う。
   - 理由: 1 つのコサイン類似度にまとめていたときは、分野のタグが少ない技術ほど分母が小さくなり、分野が合っていなくても性質だけで上位に来た。分野のタグがほとんどない Lisp 系の言語を追加したとき、架空の初心者（LV.0）の 38% で Lisp が 1 位になった。今の計算では 8%（LV.10 では 3%）。
4. 部門ごとに、スコアの高い順に並べる。各部門の上位 3 件を推薦する。部門の並び順は 6.6 の関心度で決める。
5. 推薦理由には、その技術のスコアへの寄与が大きかった ❤ カードを使う。
6. おすすめの組み合わせを決める。各フレームワークについて、`languages` の中でスコアが最も高い言語と組にする。組のスコアは「フレームワークのスコア ＋ α × 言語のスコア」とし、最も高い組を表示する。
   - α は 1 とする。0.5 では、言語の 1 位が Java の人に「Python ＋ Django」を勧めるなど、言語の好みが組み合わせに反映されにくかった。
   - スコアが 0 より大きいフレームワークがない場合（低レイヤ志向など）は、組み合わせを表示しない。

実装は `src/lib/scoring.ts`。典型的なユーザー像（ペルソナ）での推薦結果を `src/lib/personas.test.ts` で回帰テストしている。

ロジックは純粋関数として UI から切り離し、単体テストを書く。

### 6.5 タグ

#### 方針

- タグには、技術の基本的な性質だけを使う。公式ドキュメントや言語仕様で確かめられるものに限る。
- 人気、求人数、学びやすさ、書き心地など、測る人や時期で変わる主観的な指標はタグにしない。
- 重みは、下の判定基準だけで決める。基準で決まらない場合は 0 にする。
- 重みが 0 でないタグには、根拠（`evidence`）として公式ドキュメントなどの URL を残す。

#### 一覧

「適用」は、そのタグを付ける対象を表す。言 = 言語、F = フレームワーク。

**分野（9）**

| タグ | 意味 | 判定基準 | 適用 |
|---|---|---|---|
| `web-frontend` | ブラウザの画面を作る | 公式ドキュメントが主な用途として挙げていれば +1。公式のライブラリやツールで対応していれば 0.5 | 言・F |
| `web-backend` | サーバーや API を作る | 同上 | 言・F |
| `mobile` | スマホアプリを作る | 同上 | 言・F |
| `systems` | OS、組み込み、ゲームエンジンなどの低レイヤ | 同上 | 言 |
| `data-ai` | データ分析、機械学習 | 同上 | 言 |
| `ios` | iPhone や iPad のアプリを作る | Apple が公式に案内している開発言語と UI フレームワーク（Swift、SwiftUI）なら +1。iOS 向けにも公式に配布できるなら 0.5 | 言・F |
| `android` | Android のアプリを作る | Google が公式に案内している開発言語と UI フレームワーク（Kotlin、Java、Jetpack Compose）なら +1。Android 向けにも公式に配布できるなら 0.5 | 言・F |
| `cross-platform` | 1 つのコードから、異なる会社の OS 向けのアプリを作れる | iOS と Android、Windows と macOS のように、異なる会社の OS の両方に 1 つのコードから配布する仕組みが公式にあれば +1。同じ会社の OS どうし（iOS と macOS など）だけなら 0 | 言・F |
| `full-stack` | 1 つのフレームワークで、サーバー処理と画面の描画の両方を担う | 公式ドキュメントが、両方を 1 つのプロジェクトで作ることを主な用途として掲げていれば +1 | F |

**言語の性質（9）**

| タグ | 意味 | 判定基準 | 適用 |
|---|---|---|---|
| `static-typing` | 型をコンパイル時に検査する | 静的型付けなら +1。動的型付けで公式の型注釈があれば −0.5。動的型付けで型注釈もなければ −1 | 言 |
| `null-safety` | null になりうる値を型で区別する | 言語の標準で、コンパイル時に区別すれば +1。コンパイラのオプションや警告で区別できれば 0.5。動的型付けの言語は 0 | 言 |
| `native-compile` | 機械語に事前コンパイルして実行する | 機械語の実行ファイルに事前コンパイルするのが標準なら +1。バイトコードにコンパイルして VM で実行するなら 0。ソースコードをそのまま実行するなら −1 | 言 |
| `gc` | メモリを自動で解放する | 循環参照も含めて自動で回収するなら +1。参照カウントだけ（循環参照は自分で対処する）なら 0.5。自分で管理するか所有権で管理するなら −1 | 言 |
| `concurrency` | 並行処理の仕組みが言語に組み込まれている | チャネルやアクターなどのメッセージパッシング、またはデータ競合をコンパイル時に防ぐ仕組みが言語仕様にあれば +1。async/await など並行処理用の構文が言語仕様にあれば 0.5 | 言 |
| `functional` | 関数型の書き方ができる | 言語仕様に、パターンマッチ、代数的データ型（直和型）、式指向の制御構文（if や switch が値を返す）のうち 2 つ以上があれば +1。1 つなら 0.5 | 言 |
| `oop` | クラスベースのオブジェクト指向 | すべての値がオブジェクトであるか、すべてのコードをクラスの中に書くなら +1。クラスと継承はあるが必須でなければ 0。クラスも継承もなければ −1 | 言 |
| `simple-syntax` | 言語仕様が小さい | 公式のキーワード一覧に載っている語（ソフトキーワードや文脈キーワードを含む）が 40 個以下なら +1。70 個以上なら −1。その間は 0。キーワードを持たない言語（Lisp 系）は、言語仕様が再定義を禁じている名前（特殊形式など）を数える。どちらの一覧もなければ 0 | 言 |
| `homoiconic` | コードをデータとして扱える | プログラムのコードを言語の基本的なデータ構造（リストなど）で表し、それを変換するマクロが言語仕様にあれば +1。それ以外は 0 | 言 |

「F（画面）」は、フロントエンドとモバイルのフレームワークだけに付けることを表す。

|---|---|---|---|
| `batteries-included` | 必要な機能が最初から揃っている | ルーティング、DB アクセス、認証、テスト支援、コード生成 CLI のうち、本体と同じリポジトリで公式に配布されているものを数える。4 つ以上なら +1、1 つ以下なら −1、それ以外は 0 | F |

| `compile-time-ui` | ビルド時に UI のコードをコンパイルする | 実行時に仮想 DOM を使わず、ビルド時に UI のコードを DOM の操作へコンパイルするなら +1。実行時に仮想 DOM を使うなら −1。DOM を使わない（モバイル向けなど）なら 0 | F（画面） |

**開発環境とエコシステム（2）**

**知識の分野（アルゴリズム、数学、セキュリティ・暗号）**

知識の分野は、ツールではなく学ぶ内容のトピックを並べる。トピックは次の 2 種類のタグで表す。

- **内容のタグ**: そのトピックが何についての知識か。トピックごとに 1 つずつある（`data-structures`、`sort-search`、`dynamic-programming`、`graph-algorithms`、`linear-algebra`、`probability`、`discrete-math`、`calculus`、`web-security`、`network-security`、`cryptography`、`ctf`）。定義そのものなので主観が入らない。部門の専用カードで、それぞれの内容に「すき」か「パス」で答えてもらう。
- **関係する分野のタグ**: そのトピックがどの分野で使われるか。既存の分野のタグで表す。主要な応用なら 1、応用の一つなら 0.5。例: 線形代数は `data-ai: 1`、`game: 1`（3D の表示）。これにより、ほかの分野への関心ともつながる（AI に関心がある人には線形代数や確率・統計が上位に来る）。
- 関心度を判定する分野のタグとして、`algorithm`、`math`、`security` を追加する。
- 学習リソースは、公式のドキュメントがないため、公的機関（IPA、総務省、CRYPTREC）、大学（MIT OpenCourseWare）、よく知られた練習サイト（AtCoder、picoCTF）のものを載せる。
- セキュリティ・暗号部門には、「攻撃の技術は、自分の環境か許可された演習環境でだけ試す。許可なく他人のシステムを攻撃することは不正アクセス禁止法などで禁止されている」という注意書きを、結果画面の部門の見出しの下に出す。

AI・データ部門の技術には `maturity` を付けない。scikit-learn は 2007 年から公開されているが、1.0 は 2021 年で、今の基準では「新しい技術」と判定されてしまうためである（technology-weights.md の 4.5）。

#### 外したタグと理由

| 外したタグ | 理由 | 代わりに使うタグ |
|---|---|---|
| `job-market`、`enterprise`、`community` | 時期や地域で変わり、客観的に測りにくい | なし |
| `beginner-friendly`、`expressive` | 主観的な指標 | `simple-syntax`、`gc`、`fast-feedback` |
| `performance` | ベンチマークの条件で結果が変わる | `native-compile`、`gc` |
| `memory-safety`、`type-safety` | 判定が分かれやすい | `gc`、`static-typing`、`null-safety` |
| `modern` | 主観的な指標 | `maturity`（−1 が新しい技術を表す） |
| `convention`、`flexibility` | 意味が重なる | `batteries-included`（−1 が自分で構成を選ぶことを表す） |

## 7. 法的要件とコンプライアンス

前提: 完全無料、ログインなし、広告なし、人同士のマッチングなし。

### 7.1 出会い系サイト規制法

- tecupid は人と技術を結び付けるサービスで、人と人を結び付けない。そのため、出会い系サイト規制法（インターネット異性紹介事業を規制する法律）の対象にはならない想定である。
- メッセージ、プロフィール公開、ユーザー同士のマッチングなどを追加すると前提が崩れる。そのため、これらは追加しない（4.2 参照）。
- 「マッチングアプリ」という言葉は、UI の比喩として使うだけにする。対人の出会いを連想させる宣伝文は使わない。

### 7.2 個人情報保護法

- 個人情報は取得しない。回答の履歴はブラウザの `localStorage` だけに保存し、サーバーへは送らない。
- プライバシーポリシーに次を書く。取得する情報がないこと、端末内に保存するデータの内容、そのデータの消し方。
- 「データを消去」ボタンを置き、`localStorage` を消せるようにする。
- シェア用 URL には推薦結果の技術 ID だけを入れ、回答の中身は入れない。

### 7.3 外部送信（電気通信事業法の外部送信規律など）

- MVP では、アクセス解析、外部の広告タグ、トラッキング用の Cookie を使わない。
- Web フォントや CDN などの外部リソースも、できるだけ自前でホストする。
- 将来アクセス解析を入れるときは、送信先、送信する情報、利用目的を公表するページを先に用意する。

### 7.4 商標とロゴ

- 技術名やロゴの多くは商標である。MVP では**公式ロゴを使わず**、技術名のテキストと自作のアイコンで表示する。
- ロゴを使う場合は、各プロジェクトのブランドガイドライン（トレードマークポリシー）に従う。
- 「各技術の提供元とは関係のない非公式サービスである」とサイト上に明記する。
- サービス名「tecupid」について、公開前に J-PlatPat で同じ名前や似た名前の商標がないか確認する。

### 7.5 著作権

- 特徴カードの文や技術の概要は、すべて自分で書く。公式ドキュメントや他サイトの文章は転載しない。
- tecupid 自身のコンテンツ（カードの文、ドット絵など）については、著作権の表示や主張をしない。Claude で作った部分が多く、AI で作ったものに著作権が認められるかもはっきりしないため。リポジトリ全体を MIT ライセンスで公開する。
- 外部の資料はリンクで紹介するだけにする。
- 依存ライブラリのライセンスを確認する。リポジトリ自体のライセンスも決める（10 参照）。
- フォントの DotGothic16 は SIL Open Font License 1.1 で提供されている。npm パッケージ（@fontsource/dotgothic16）としてビルドに含めて配信し、著作権表示とライセンスを「tecupid について」のページに載せる。
- ドット絵（キューピッド、ハートなど）はすべてオリジナルで、`src/components/sprites.ts` に文字の並びとして描いている。

### 7.6 既存サービスとの関係

- スワイプは一般的な UI パターンとして使う。既存のマッチングアプリの名前、ロゴ、配色、画面の見た目は真似しない。
- ボタンやスタンプの文言は「すき」「興味なし」とし（最初は「パス」だったが、「すき」の反対の言葉になっておらず、しっくりこないという意見があったため変えた）、既存のマッチングアプリで使われる「LIKE」「NOPE」は使わない。
- ドット絵の見た目は、特定のゲームのキャラクターや画面を真似しない。メッセージウィンドウ風の枠などは、ジャンルで広く使われる表現の範囲にとどめる。
- 海外では、スワイプ操作に関する特許を持つ企業の例がある。そのため、主な操作はボタンにし、スワイプは補助の操作にとどめる。公開範囲を広げる前に、必要に応じて専門家に確認する。

### 7.7 免責

- 推薦結果は学習の参考情報であり、キャリアや就職での成果を保証しないことを、利用規約と免責事項に書く。
- 技術の情報は作成時点のものであることを明記し、最終更新日を表示する。実装では `DATA_UPDATED`（`src/data/technologies.ts`）を、結果画面と「tecupid について」に表示している。

### 8.1 デザイン

- **ターミナル × ドット絵**にする。エンジニア向けらしく、昔の端末の画面の雰囲気に、ドット絵のキューピッドとハートを組み合わせる。
- 配色は「ターミナルの緑」。黒い背景に緑の文字で、ハートのピンクを差し色にする。端末らしさを優先して配色は 1 種類だけにし、ダークモードの切り替えはしない。色はすべて `:root` の CSS 変数で定義する。
- 端末らしい表現:
  - カード、おすすめの組み合わせ、シェアされた結果は、ターミナルのウィンドウ（タイトルバーと 3 色のドット）で囲む。カードには `$ tecupid next` のプロンプトと点滅するカーソルを出す。
  - 「すき」「興味なし」のボタンはキーボードのキー風にし、`y` と `n` のキーでも答えられるようにする。
  - 見出しは `//`（コメント）や `#`、`##`（Markdown）の記号で始める。進捗は `[■■■□□□] 3/17` のようなゲージにする。
  - 画面全体に薄い走査線を重ねる。
- フォントは DotGothic16。ドットがにじみにくいよう、文字の大きさは 16px、24px、32px、48px を使う。
- 枠は CSS の `box-shadow` で描き、角を 1 ドット欠いてドット絵らしくする。
- スプライトは文字の並び（`src/components/sprites.ts`）で描き、SVG で表示する。拡大率は整数にして、輪郭をにじませない。
- アニメーションは 2 コマの切り替え（`steps()`）にする。`prefers-reduced-motion` のときは止める。

## 9. 技術スタックと構成

| 項目 | 選定 | 理由 |
|---|---|---|
| 実行基盤 | **Cloudflare Workers（確定）** | 完全サーバーレス。静的アセットの配信は無料プランでも使える |
| フレームワーク | Astro と React（スワイプ画面だけをアイランドにする）（案） | 静的サイトが中心で軽い。yonu-astro-page で使い慣れている |
| 言語 | TypeScript（案） | データモデルを型で守れる |
| テスト | Vitest（案） | スコアリングの単体テスト用 |
| デプロイ | Wrangler（案） | Workers の公式 CLI |
| CI | GitHub Actions（案） | テスト、データ検証、デプロイ |

### 9.1 構成

- Astro で静的ビルドした `dist/` を、Workers の静的アセット機能（Workers Static Assets）で配信する。
- 推薦の計算はすべてブラウザで行う。MVP では Worker のスクリプト（サーバー側の処理）は書かない。
- 将来サーバー側の処理が必要になったら（例: シェア用 OGP 画像の動的生成）、同じ Worker にスクリプトを追加する。その場合も個人情報は扱わない。

### 9.2 公開

- URL は `https://tecupid.yonu.work`。yonu.work は Cloudflare で管理しているドメインで、ドメインそのものは別のサイト（yonu-astro-page）なので、サブドメインを使う。Workers の独自ドメイン（`wrangler.jsonc` の `routes`）で配信し、DNS のレコードと証明書は Cloudflare が自動で作る。
- まずベータ版として公開する。`src/config.ts` の `BETA` が true のあいだは、次のようにする。正式に公開するときは false にする。
  - ロゴの横に「BETA」を表示し、「tecupid について」に、内容や推薦の仕組みが予告なく変わりうることを書く。
  - 検索エンジンに載せない（`<meta name="robots" content="noindex">`）。SNS のサムネイル（OGP）は出る。
- 問い合わせ先は GitHub の Issues。そのため、GitHub のリポジトリを公開する。
- 載ってほしい技術は、Issue のテンプレート「技術の追加リクエスト」で受け付ける。タグを客観的な基準で付けられるよう、公式ドキュメントの URL を必須にする。結果画面の一番下と「tecupid について」から、このテンプレートにリンクする。
- 公開リポジトリでは外部の人のプルリクエストでも CI が動くので、CI にはリポジトリを読む権限（`contents: read`）だけを与える。CI は秘密の情報を使わない。
